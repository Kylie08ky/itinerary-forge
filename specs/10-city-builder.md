# 10 任意目的地：按需现建城市

> 来源：你 2026-10-29「我希望不管用户输入什么作为旅行目的地，都可以生成一份攻略」。你的取舍：**现建要先准（建城时把交叉核对做完，等 3–5 分钟）；输入的是国家或地区时，列出这个国家最常去的 5 个城市让用户选一个**。
> 这份规格取代 10-29 上午的「`build_city` 手动命令 + 种子审阅」方案：手动命令只剩「开发者想预建 / 精校某座城市」的用途，**产品里不再需要我一座一座加**。
> 状态（2026-11-06）：阶段 1–4（H1–H4）已做完，你 2026-10-31 确认；之后在这份规格上陆续加了名气与「均衡」选点（H19）、主题增至 8 个（H20）、热度与维基导游推荐（H21）、当地名菜（H22），都已确认，见 [05 进度清单](05-progress-checklist.md)。

## 一、结果

用户在新建页 / 一句话填表里写任何一个目的地：
- **库里有（巴黎、周边一日游城市）**：和现在一样直接生成。
- **库里没有（大阪、里斯本、成都……）**：系统先认出这座城市（维基数据：坐标、国家、时区、币种、当地语言），然后**自动现建一份城市数据**（选点、核对、分主题），建完生成行程；建好的城市存下来，下次同一座城市秒出。
- **输入的是国家 / 地区（日本、意大利）**：弹窗列出这个国家最常去的 5 个城市，让用户选一个。
- **同名城市**（Paris 在法国和美国得克萨斯）：名气最大的当默认，名气接近的弹窗让用户选。
- **认不出来**：明确告诉用户「没找到叫这个名字的目的地」，不瞎猜。

现建的城市是「标准档」：主题、地图、排程齐全，但**价格、预约渠道、部分闭馆日是「待核对」，页面写「以官网为准」，不编**。精校过的（巴黎，以及你我之后补了精校的）质量更高。

## 二、现建流程（全部来自公开数据，不让模型编）

1. **认城市**：维基数据按名字搜（中文 / 英文 / 当地语言都行），只收「城市 / 城镇」类并有坐标的条目；国家条目走「5 个城市」；候选名气接近且在不同国家 → 让用户选。
2. **城市配置**：中心点、国家（ISO 代码）、币种（国家的官方货币）、时区、当地语言都来自维基数据；夏令时 / 标准时差由时区算；市区范围（`bbox`）按中心点上下左右各约 0.25° 起，种子里写了就用种子的。
3. **候选**：中心点周围 30 公里内、维基数据语言版本数 ≥ 门槛（欧洲 20、其他 10）的景点类条目；去同一个地方的重复条目、去「属于另一个候选的一部分」、去类别不对的；取前 40 个。**市区范围外的只有种子里指定的才收**（一日游）。
4. **逐点自动核对**：坐标来自维基数据，和 OpenStreetMap 交叉（大景区放宽到 500 米，一般 150 米；差得多的标出来）；官网来自维基数据 / OSM，能打开才收；每周闭馆日来自 OSM 的开放时间（标「社区数据」）；价格、预约、优惠拿不到一律「待核对」。
5. **分主题**：按类别归到古迹 / 博物馆 / 街区与美食 / 自然公园，没有成员的主题不建；前 6 名是锚点，其余是辅助点。
6. **叠加精校**：`data/city-overlays/<id>.json` 里有来源和日期的事实覆盖草稿里的「待核对」（现在有北京故宫：周一闭馆、须提前订票）；重新建不会丢。
7. **存下来**：现建的数据放在 `data/generated/`（不进仓库，因为是自动产物；精校的放 `data/city-overlays/`，进仓库）；下次直接读。

## 三、结构

```
app/citybuild/                  # 内核（不联网的纯函数 + 取数据）：去重、去一部分、分主题、坐标核对、精校叠加、审阅表、认城市、造城市配置
scripts/build_city.py           # 命令行：预建 / 重建某座城市，写审阅表（开发者用）
data/city-seeds/<id>.json       # 可选种子：补充名单（长城这类）、排除名单、市区范围；没有种子也能建
data/city-overlays/<id>.json    # 精校（进仓库）
data/generated/                 # 现建的城市数据（不进仓库）
tests/test_citybuild.py         # 内核的单元测试（录好的样本，不联网）
```

## 四、城市档位

`City.tier`：`full`（精校，巴黎）/ `standard`（现建，价格 / 预约 / 部分闭馆日待核对）/ `light`（一日游目的地）。行程页「注意事项」对 `standard` 多写一句「这座城市的数据是自动建的……」。`City.currency` 放开到任意 ISO 货币代码（现建城市用所在国货币；预算里没有价格的点照旧标「待补」，结算币种仍是人民币 / 欧元）。

## 五、国内的特殊处理（M17 S4–S6 不变）

中文名优先、国内不加当地语言名；预约渠道（官网 / 公众号 / 小程序 / 实名）自动拿不到，只进精校；老字号餐厅这一轮不做（品牌条目没有坐标）。国内 OSM 坐标有偏移的情况：大景区放宽后仍对不上的，标「坐标差得多」，不丢。

## 六之二、新建页的顺序和统一（你 2026-10-29 试了上海、西西里之后的反馈）

- **先填目的地，再选主题**：新建页「行程信息」（目的地、日期、预算、节奏）放最上面，下面才是「选主题」（含深度路线）。目的地默认空；**没认出城市之前不显示任何主题和路线**（以前一开始显示的是巴黎的），只有一句「先在上面填目的地」。目的地填好（离开输入框 / 回车）就立刻去认、去建，不等到点「生成」；认出之后主题、深度路线、候选地点都换成这座城市的。链接可以带 `?destination=Paris`。
- **城市本身就是城市时不再追问区**：上海、东京、新加坡这类既是行政区又是城市的，直接当城市（以前「上海」会弹出「浦东新区 / 杨浦区」）；只有地区（西西里、托斯卡纳）和国家才列城市。名字和输入一样的候选排在前面（「北京」不会被名气更大的国家抢走）。
- **日期统一**：开始 / 离开日期不管从哪里改（顶部一句话、行程信息、来回交通），到达 / 返程出发那天、去程出发和返程到达（按同样的天数平移，夜里的航班仍是前一天出发）、住宿里正好是原来开始 / 离开日的入住 / 退房，都一起跟着变；反过来在来回交通里改到达日，开始日期也跟着变。
- **随行、预算按城市**：现建的城市的行李清单没有巴黎 / 申根 / 法国 / 欧元的内容（护照、签证、转换插头、现金币种都写通用说法并以官方为准；国内城市改成身份证和手机支付），气温用当地去年每月的平均最高气温；推荐待办同理；**预算不估算**（门票和交通价格没核对），预算卡写明原因，PDF / 导出里不写费用估算一节。

## 六之三、图片、简介和景点来源（你 2026-10-29 试了重庆之后的反馈）

- **你的反馈**：重庆除了第一天全是「自由安排」；顶部一句话里的目的地没有填进「行程信息」；每个目的地要有封面图、景点要有图片和具体信息；问现在是不是不支持多城市。
- **重庆为什么只有 2 个景点（证据）**：维基数据按「语言版本数 ≥ 10」选，重庆的景点（洪崖洞、湖广会馆这类）语言版本很少，门槛一卡就只剩 2 个，而且排在前面的大多是跨江大桥。中国城市在维基百科里的覆盖本来就比欧洲、日本弱——**这是开放数据的上限，不是排程的问题**。
- **改进（建城流程第 2 版，`BUILDER_VERSION = 2`）**：名气门槛先按城市大小、点不够就放到最低；无名的桥不算景点；点还不够，再用 OpenStreetMap 里带维基数据编号的景点 / 博物馆 / 公园 / 观景台补充；找到的景点少于 6 个就不建，并明说「要等接入地图服务（高德）之后才够用」；少于 20 个时行程说明里提醒「天数多的话会有空白的天」。重庆从 2 个变成约 30 个（洪崖洞、湖广会馆、十八梯、三峡博物馆……）。
- **图片和简介**：每个地点的图片来自维基数据的「图像」，下载自 Wikimedia Commons，授权在白名单里（CC0 / 公有领域 / CC BY / CC BY-SA）、作者和来源链接齐全才收，署名在地点卡上；封面大图取最有名的几个地点里第一个有合格大图（≥ 1600 宽的 JPEG、≤ 900KB）的，成为这座城市的首页 / 行程封面；简介是中文维基百科摘要的前两句，带来源。存在 `data/generated/{photos,hero,media}/`，运行时不再访问 Wikimedia。没有合格图片的地点就没有图，不用占位图。
- **旧版建的城市自动重建**：城市配置里记着 `builder_version`；版本低的现建城市下次有人输入它的名字就按新流程原地重建（城市 id 不变，已有行程照常打开）。
- **一句话里的目的地**：「去日本玩」以前读不出来（「日」被当成日期用字了）；现在读出后填进「行程信息」，不在库里的马上去认 / 建；一句话里原来那条「第一版建议 2–5 天」的提醒删掉（时长提示由表单按目的地给）。
- **多城市**：现在一次行程只有一个目的地；「北京 → 西安」这种在 [M17 K3](modules/M17-cities-and-multi-city.md)，还没做。

## 六之四、门票合计和随行清单（你 2026-10-29 看了重庆行程之后）

- **门票合计不再写 €0**：封面统计、行程页、导出 HTML 里，一座城市一个票价都没有（现建的）就写「待补」；有票价的（巴黎）照旧。币种跟目的地：显示用目的地的币种符号（€ ¥ $ £ …），现在库里的票价都是欧元，人民币票价和国内预约渠道随 K1 余项另做。
- **随行清单更贴这座城市、这趟行程**：在通用模板之外，按这座城市去年同期的气候（降水、早晚温差、海拔、偏热偏潮）和这份行程里的地点（教堂 / 寺庙要穿得得体、户外多 / 爬山要防滑鞋、这趟大半时间在户外）加几条只属于这趟的建议，并写出是哪几个地点 / 哪个数字（「当地去年同期月降水约 180 毫米」「行程里有：圣母院、……」）；没有数据的项不出现，不编。气候数据建城时从 Open-Meteo 历史数据取（`BUILDER_VERSION` 升到 3，旧的现建城市下次输入时自动重建）。这些都是经验性建议，不当事实。
- 还没做、也不会编的：转换插头的型号、签证要求（需要有来源的国家数据）。

| 编号 | 验收场景 | 预期 |
|---|---|---|
| H12 | 打开现建城市（重庆）的行程页，看封面统计 | 「门票合计」是「待补」，不是 €0；巴黎行程仍是 € 金额 |
| H13 | 重庆行程的「随行」→ 行李清单 | 除了通用项，有按当地气候 / 行程地点的几条（如教堂着装、户外防晒、雨水多、温差大），带具体数字或地点名；和巴黎的清单明显不同 |

## 六之五、随行清单按国家、国内、学生定制（你 2026-10-31）

**假定用户是中国人**：
- **国内城市**：不带护照 / 签证 / 转换插头，带**身份证**（住宿登记、景点实名预约都要）和手机支付；**香港 / 澳门**带往来港澳通行证和有效签注（以出入境管理部门规定为准）。
- **学生**（出行人里勾了「学生」）：国内带**学生证**（景点学生票、部分交通优惠凭证件）；国外加 **ISIC 国际学生证**（官网：100 多个国家有学生优惠），欧洲尤其提前办（很多景点、博物馆、交通对学生有优惠，具体以各景点规定为准）；巴黎的清单也一样。
- **热门国家的数据**（`data/companion/countries.json`，`scripts/build_countries.py` 生成，23 个：日本、韩国、泰国、新加坡、马来西亚、越南、印尼、美国、英国、德国、意大利、西班牙、法国、瑞士、奥地利、荷兰、希腊、葡萄牙、捷克、澳大利亚、土耳其、阿联酋、中国香港）：
  - **转换插头**：当地插座类型 / 电压 / 频率来自维基百科「Mains electricity by country」那张表，并和国内（A、I 型，220 V）比：有相同型号就说「多数国内插头能直接插，仍建议带一个备用」，没有就说「要带转换插头」；电压低于 220 V 的（日本 100 V、美国 120 V）提醒看铭牌。
  - **签证**：**不写任何国家的签证政策**（免签 / 落地签说变就变），只给该国官方的签证 / 入境页面链接，**链接要能打开才收**（官方域名但自动请求被拦的按地点官网同一条规则记 `bot_protected`）；越南、西班牙的官方页面没能核对，不写链接，页面写「以目的地国家的官方渠道为准」。
  - **申根国家**共用一条护照规则（离开申根区后还要有 3 个月以上、签发不满 10 年），来源是法国签证官网那条已核对的事实。
  - 没有整理的国家：通用写法，不编。
- 还没做：支付习惯、小费、紧急电话、当地交通卡（要有来源的数据，之后按国家补）。

| 编号 | 验收场景 | 预期 |
|---|---|---|
| H14 | 目的地填「日本」下的大阪（或东京），出行人勾一位学生，生成后看随行清单 | 转换插头写「A / B 型，100 V / 50 / 60 Hz，……有相同的 A 型……电压比国内低」；签证写「以日本外务省为准」带来源链接；有「学生证原件和 ISIC 国际学生证」；没有申根的「3 个月」那条 |

**实测（2026-10-29，真实的维基数据 / OpenStreetMap）**：「里斯本」认城市约 8 秒，现建 25 个点用了约 2 分钟，生成了 4 天行程（古迹 22 个、博物馆 3 个）；「日本」「意大利」「美国」各列出 5 个城市；「xyzabcqq」认不出；「大阪」「里斯本」「Paris」认成城市。
**已知的粗糙处**：自动选点有杂质（比如跨河大桥算景点）；候选里「人口 > 30 万」才进国家的城市列表（威尼斯这类小城不会出现，直接输入城市名可以）；Windows 上要 `tzdata` 包提供时区数据库（已加进依赖）。
