# 08 真实旅行驱动：Q3 排程方案 + 周边一日游 + 南意 5 天

> 来源：你 2026-10-24 的决定与需求。状态（2026-10-28）：**Q3 排程 ✅、周边一日游 ✅（§3.4–3.7）、P17 深度游学路线 ✅（见 [09](09-deep-routes.md)）已做完；南意圣诞后来做成了意大利实测（[12](12-italy-trial.md)，十座城市精校覆盖，已做完）**。
> 目的：用你**真实要出的两趟旅行**来验证产品，而不是继续在巴黎上自我测试。

你的决定：P17（主题式深度游学路线）放在长行程（Q5）之前；**提前收尾**（协作账号、AI 伴游推到交付之后）；
你最近的两个真实需求：

1. **德国境内外的城市一日游**：住斯图加特，想看附近哪些城市值得一日游；住亚琛，想看附近有什么好玩的，可以去荷兰、比利时。
2. **圣诞节前后、约 5 天（一周以内）的南意旅行**，和朋友一起。

## 一、先说结论

- 这两个需求其实是**同一个能力**：**「一个落脚点 + 每天可以去不同的城市」**。南意 5 天最合理的走法就是住在那不勒斯（或索伦托），每天出发去庞贝、阿马尔菲海岸、卡普里；斯图加特 / 亚琛的一日游是同样的模型，只是落脚点在家里。所以做一套，两边都用。
- **全部是欧元区、同一个时区（中欧时间）**：币种、时区、汇率这些现成的城市配置（K0）够用，不用改。
- **现在产品做不了的 4 件事**（我读了代码后确认的）：
  1. 行程里的一天只能待在**一座城市**（`Day` 没有"这天去哪座城市"），而你的两个需求都是「每天去不同的地方」；
  2. 地点库只有 `closed_weekdays`（每周几闭馆），**没有"某年某月某日闭馆"**，而圣诞节（12/24、12/25、12/26、1/1）正是景点最容易关门或改时间的日子；
  3. 没有「**从 A 城去 B 城要多久、怎么去**」的数据（城际时间）；
  4. 没有「**我住这里，附近哪些城市值得去**」的推荐入口。
- **关键风险是数据不是代码**：每座目的地城市都要逐个点核对官网、坐标、开放时间（我们的硬规则：事实只信带核对记录的策展数据）。数据量见第四节。

## 二、Q3 排程（先做，1–1.5 天）：让"均衡"和权重真的起作用

依据是 Q1 基线的发现：混选的权重几乎不起作用（5:3:1 实际 6/7/6 个点）；8 个主题全选时娱乐、亲子各只有 1 个点；有的天只有 1 个点；紧凑节奏常常没有午饭。

| 改什么 | 怎么改 | 验收（用 Q1 基线量） |
|---|---|---|
| **权重生效** | 点数按权重用"最大余数法"分配到各主题，不再被候选池的先后顺序带偏 | 混选 3 主题权重偏差 0.24 → **≤ 0.15** |
| **每个主题至少 2 个点** | 所选主题数 ≤ 总点数 ÷ 2 时，每个主题至少 2 个点；主题太多排不下时（如 8 主题 4 天）保证每个主题至少 1 个点，其余按权重分 | 8 主题全选 5 天以上：每个主题 ≥ 2 点；任何情况 8/8 都有点 |
| **均衡 = 地标优先** | 均衡模式先排城市配置里的"必看地标"（巴黎的埃菲尔铁塔、卢浮宫等），再让各主题均匀补满；这样"不知道哪里好玩"的人拿到的就是最经典的一组 | 均衡的前几个点都是地标；每天 ≥ 2 个点 |
| **每天至少 2 个主要点** | 排完检查：某天不足 2 个就从别的主题借主要点（不是只补公园）；借不到才用小点并标出来 | 8 主题 5 天不再有"只有 1 个点"的一天 |
| **午饭不能跳过** | 每天（含紧凑、到达日、一日游日）在 11:30–14:30 里保证一顿午饭：轻松 / 均衡 60–90 分钟，**紧凑 20–30 分钟（快餐 / 面包）**；到达日如果到达时间晚于 14:00、离开日如果 12:00 前离开则没有午饭 | 所有请求（含紧凑）午餐天数 = 天数 |
| 不退步 | 质检错误仍 0、重复地点仍 0、排程耗时不超过现在的 5 倍 | 重跑 `scripts/eval_schedule.py` 对比，报告更新进 `docs/reports/` |

不做：不改巴黎地点数据，不动 LLM 的部分（排程只用确定性算法）。

## 三、周边一日游 + 南意 5 天：产品怎么长

### 3.1 你会怎么用（两个流程）

**流程 A：从家出发看看周边（斯图加特 / 亚琛）**

1. 新建页顶上选「**从我住的地方出发看看周边**」，选出发地（斯图加特 / 亚琛）和想出去的日期。
2. 看到一个**周边目的地列表**：每个目的地写着单程多久（火车 / 汽车，来自核对过的数据）、能玩几个小时、**这个季节有什么**（比如圣诞市场的日期）、一两句亮点；按"单程时间 / 主题 / 当季"排序。
3. 点「**排一天**」→ 生成这一天的行程：出发时间、2–6 个点、**最晚返程提醒**，也可以选几天各去一个城市，拼成一份多天行程（每天标明去哪座城市）。
4. 其余和现在一样：改行程、导出、PDF、预算、清单。

**流程 B：南意 5 天（圣诞）**

1. 新建页选「**城市游 / 区域游**」，选"南意"，填日期、交通（到达时间决定第一天）、人数。
2. 默认方案：**住那不勒斯 4 晚**，每天一座城市——那不勒斯老城、庞贝 / 赫库兰尼姆、阿马尔菲海岸（索伦托 / 波西塔诺 / 阿马尔菲）、卡普里（若船班允许）。
3. 每个点会写：**这一天是不是节假日闭馆、需不需要提前订票**（庞贝、考古馆这类）、冬季船班风险（核对后才写）。
4. 另一条备选路线（住马泰拉 / 普利亚）后做，**不挤在第一版里**。

| R0-b | **具体日期闭馆** | 地点增加 `closed_dates`（每年固定的月日，如 12-25、01-01）和 `date_notes`（12/24 提前闭馆这类带说明的）；排程器和质检都按日期避开 | 0.5–1 天 |
| R0-c | **城际时间表** | `data/cities/city-pairs.json`：从哪里到哪里、方式、分钟、官方来源、核对日期、"最晚返程"提示。**只收核对过的**，没有就写"待补"，永远不让 AI 编；订票只给官方链接（DB、Trenitalia、Italo），不做抓取 | 0.5 天（代码）+ 数据 |

R0 的代码合计约 **3–4 天**，R1 / R2 的主要时间是**逐个点核对事实**。

### 3.3 目录结构与选型（动手前请你确认）

- `data/cities/<id>.json`：每座城市（出发地、目的地）一份配置；新增字段 `tier`（`full` 巴黎这种完整库 / `light` 一日游目的地）、`region`（如 `suedwest-de`、`nl-be-grenzland`、`sued-italien`）。
- `data/cities/city-pairs.json`：城际时间表（M17 原定的名字，沿用）。
- `data/places/<id>.json`、`data/themes/<id>.json`：和现在一样按城市分文件；`light` 城市共用一个"一日游"主题。
- `data/seasonal/events.json`：季节性活动。
- `app/daytrips.py`：周边推荐（筛选 + 排序，纯算法）；`GET /daytrips?from=stuttgart&date=2026-12-12` 返回列表；排程仍走现有排程器，只是每天可以换城市。
- 前端：新建页加「城市游 / 周边一日游」入口；周边列表页（可复用现在的 `PlaceCard` 风格卡片）。
- 选型：**不引入新的第三方依赖**；城际时间和票价只用人工核对的数据，不接 Google / 高德 / 12306 / DB 的接口（避免条款与稳定性问题）；地图仍是 OpenStreetMap。

### 3.5 周边一日游第一批实现情况（2026-10-25，你「方案同意」后做的）

- **数据**：14 座目的地（斯图加特 7 个、亚琛 7 个）各有 10–11 个点（维基数据 SPARQL 按知名度挑，OSM 补开放时间 / 官网，全部标「开放数据草稿」，来源和日期见每个点的 `draft_source`）；城际时间表 `data/cities/city-pairs.json` 14 条（Transitous 查的，带来源、查询日期、样例日、当晚末班返程）；圣诞市场 7 个（`data/seasonal/christmas-markets.json`，`confirmed_by`：官方网站我亲自打开核对过的只有海德堡、斯特拉斯堡，其余 5 个只是活动聚合网站 / 搜索摘要，页面上写明「日期没能在官方网站核对，出发前请确认」）。
- **代码**：城市 `tier` / `region`；地点 `data_status` / `draft_source` / `closed_dates` / `date_notes` / `season`（不在期内当作闭馆，排程器和质检都认）；`TravelRequest.day_trip_from`（一日游：到站只留 10 分钟、返程提前 30 分钟，不当晚到 / 早走日，接驳项写「从斯图加特 Stuttgart 出发，抵达…」）；`app/daytrips.py`；接口 `GET /daytrips/origins`、`GET /daytrips?origin&date`、`GET /daytrips/request`（交给现有的 `POST /tasks`）；前端 `/daytrips` 页 + 导航入口；地点卡标「开放数据草稿」和「当季活动」；行程页 / 分享页的地点库跟着行程自己的城市走（`city_id`）。
- **默认返程时间**：没填时平常 18:30；当天有圣诞市场在期内留到 21:00；都不晚于样例日的末班；填的返程比末班晚会提示。
- **已知局限**：中文名取维基数据简体标签，没有简体就用繁体（如「聖靈教堂」），连繁体都没有就直接用当地名；价格、开放时间、圣诞节当天开不开都没核对；多座城市拼成一份多天行程（R0-a）和南意一起做。

### 3.6 一日游的行程页（2026-10-25，你验收时的反馈；**这一版已改**）

一日游是「住在 A 城，当天坐火车去 B 城再回来」，和出国旅行不一样。行程页按这些规则：

- **没有「随行清单」**（行李 / 待办 / 文件三个页签整张卡都不要），页内目录不列「随行」，分享弹窗不给「行李清单 / 待办」的勾选（「行程备注」保留）。你的原话：德国境内的一日游整体不需要；**出境的（斯特拉斯堡、列日、马斯特里赫特、布鲁塞尔）只在行程里提醒带护照**：第一项接驳（「从斯图加特 Stuttgart 出发，抵达…」）的备注开头写「出境：带好护照（或居留卡）原件。」，德国境内的不写。（我之前做的一日游专用行李 / 待办模板已删除。）
- **没有预算估算**：一日游没有核对过的价格数据（门票是草稿，火车票以 DB Navigator 为准）；预算接口返回 404 和原因，预算卡换成一句说明，导出不写费用一节，填了预算上限也不按预算调整。
- **没有住宿卡**，页内目录也不列「住宿」。
- **标题和日期**：标题写「海德堡 Heidelberg · 一日游」，副标题「2026-12-12 · 从斯图加特 Stuttgart 出发」；封面只写一个日期（12.12），**不写「10.25—10.25」和「共 1 天 0 晚」**；不显示内部的主题代号「daytrip」，也不显示预算档位；封面统计不放「门票合计」。
- **封面卡片**：多天行程每天一张亮点卡；只有一天时那一天的前 5 个地点各一张（不再只有一张博物馆卡）。
- 接口：行程详情新增 `day_trip_from`、`day_trip_info`（`{city: 「海德堡 Heidelberg」, origin: 「斯图加特 Stuttgart」}`），没有时不出现。
- 验收：浏览器验收新增：排一份海德堡一日游，没有住宿 / 随行卡、标题和封面如上、封面至少 3 张卡；斯特拉斯堡那份第一项带「护照」，海德堡那份不带。

**周边一日游页面**（版式已按你的反馈重做，不改数据和接口）：

- 顶部是一块选择栏：「出发地」两个大按钮（斯图加特 Stuttgart / 亚琛 Aachen），日期、出发时间、最晚返程三个带标题的输入框，四项排成一行、高度一致；窄屏上下排。

### 3.7 出发地改成你的居住地址、区分区间火车和 ICE（2026-10-25，你的两条新要求；**你已「方案同意，四条都按建议」**）

**我先核对了可行性（2026-10-25 实测），结论：两条都能做，而且正好用现在已经在用的 Transitous，不用新注册任何服务。**

1. **Transitous 能分出火车种类**：同一条线路它会返回好几种走法，每一段带类别。斯图加特 Hbf → 海德堡 Hbf（周六 09:00 左右）实测：**ICE 直达 39 分钟、IC 直达 46 分钟**（都属 DB 长途，要另买票），**只坐区间车（RE，换乘 1 次）79 分钟**（Deutschlandticket 覆盖）。也就是说，我现在页面上写的「42 分钟」其实是 ICE 的用时；你有月票的话实际要 79 分钟，这一点之前没讲清楚。
2. **Deutschlandticket 覆盖范围**有 DB 官方页面（bahn.de/angebot/regio/deutschland-ticket，我 2026-10-25 读了）：区间 / 本地列车（RB、RE、S-Bahn）、公交、有轨电车、地铁都含；**DB 长途（ICE、IC、EC）不含**；月价 63 欧，2027-01-01 起 66.80 欧。页面没写跨境怎么算，所以跨境一律写「跨境段另买票，以 DB 为准」，不替官方下结论。
3. **居住地址**：Transitous 的 `/geocode` 能把「Königstraße 28, Stuttgart」查成坐标（实测返回门牌级结果），再用坐标直接查「门到车站到目的地」的路线（实测 0.5 秒一条，含步行和地铁），所以出发地可以是任意地址，不再固定两座城市。
4. **票价**：没有开放的票价数据，我不编。页面给「在 DB 查实时班次和票价」的链接（bahn.de 搜索页，预填起终点和时间），价格以 DB 为准。DB 官方有开发者接口（需要注册申请密钥）和社区维护的非官方接口，都不建议现在用：前者要你申请，后者随时可能失效。

**方案（建议）**：

- **出发地**：页面顶部填「你的住址」（街道 + 城市），搜出最多 4 个候选地址让你点选确认；记在你自己的浏览器里，下次不用再填。没有填时，仍可选斯图加特 / 亚琛的市中心作为快捷入口。
- **目的地**：仍然是我们已经收录的 14 座城市（斯图加特周边 7 个、亚琛周边 7 个）。住在别的地区，附近没有收录的目的地时，页面明说「附近还没有收录目的地」，新增城市用现有的开放数据脚本批量建（一批 7 座约 1 天）。
- **单程用时**：改成从你的地址出发，**打开页面时现查**（实测公共服务一条路线要 2–3 秒、而且是排队处理的，所以 7 座城市的目的地列表约 20 秒；同一天同一地址 3 小时内再看是缓存、很快）；查不到时回退到现在存好的「市中心车站」时刻表，并写明「这是从市中心车站算的」。这会让应用运行时第一次联网查 Transitous（免费公共服务，我会带联系方式的 User-Agent、限制并发）。
- **火车种类**：每座目的地的卡片给两个选项，用你打勾的「我有 Deutschlandticket」决定默认显示哪个：
  - 「最快」：写清楚车次类别（如 ICE 2090，39 分钟，**需另买票，价格以 DB 为准**）；
  - 「只坐区间车」：RB / RE / S-Bahn（如 RE1 → RE71，79 分钟，换乘 1 次，**有 Deutschlandticket 就不用另买票**）；
  - 没有区间车方案的（如国境线外的斯特拉斯堡），只显示最快并写「需另买票」。
- **「排一天」**：到达时间、末班返程都按你选的那个选项算；第一项接驳写明坐哪类车（「乘 RE1 / RE71 区间车」或「乘 ICE 2090」）。
- **「在 DB 查实时班次和票价」链接**：每张卡一个。**我在浏览器里试了 bahn.de 的预填链接：只带站名和时间（甚至加上站点编号）打开后起点终点是空的、日期是今天，没法预填**（DB 的链接要带它自己的站点内部编码，我们没有，也不去猜）。所以链接只到 DB 的搜索页，要填什么（「Stuttgart Hauptbahnhof → Heidelberg Hauptbahnhof，12 月 12 日 09:56」）写在链接旁边。
- **地址的隐私**：地址只存在你自己的浏览器，行程里**不保存街道地址**，只写出发地的城市名和车站（如「从斯图加特 Stuttgart 出发」）；分享 / 导出里也只有这个。地址会被发给 Transitous 查询（公共服务，不登录）。
- 验收：填一个斯图加特的地址 → 目的地列表的用时是「从这个地址出发」的，海德堡能同时看到 ICE 39 分钟和区间车 79 分钟两个选项；勾上 Deutschlandticket 后默认显示区间车；排一天的第一项写乘哪类车；换一个亚琛的地址能看到亚琛周边。

**住址找不到时（你的反馈）**：地址查询对「街道 门牌号, 邮编 城市」最灵，下面这些会让它认错或找不到，现在都处理了——楼层 / 房间 / 楼栋（「3.
