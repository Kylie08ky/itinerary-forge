# 11 多城市旅行（K3）

> 来源：你 2026-10-31「先做多城市，高德等我拿国内手机号注册」。需求在 [M17 S8–S10](modules/M17-cities-and-multi-city.md)，这里是做法。
> **现状（2026-11-06）：第 ①–⑥ 批都已做完并确认**（2026-11-02 验收通过）。做法后来改成**一份行程、每天标城市**（第 2 版），不再是「几份单城市行程串起来」，下面前几节写的是当时的难点和旧方案，**以第八节和第 2 版为准**；一份行程最多 8 座城市。多城市的一句话修改先不做。

## 一、难点（证据）

现在一份行程 = 一座城市：全站有 **131 处**按「这份行程在哪座城市」取数据（地点库、预算、行李、天气、时区、地图、导出、编辑、质检……）。如果把一份行程改成「每天一座城市」，这 131 处都要改，风险大、容易出错。

## 二、我提议的做法：「多城市旅行 = 几份单城市行程串起来」

- **每一段（城市）就是一份普通的单城市行程**，完全复用现有的排程、编辑、预算、行李、导出、天气、地图——这些都不用改，也不会被改坏。
- 新增一层「**旅行**」（`trip`）：有序的几段（最多 8 段，每段自己的开始 / 离开日期，一座城市可以只待一天）+ 段与段之间的**交通段**（方式、出发 / 到达时间、车次、确认码）。
- **移动日**：交通那天，前一座城市只排到「出发时间 − 到站 / 到机场的提前量」（高铁 90 分钟、飞机 150 分钟）之前，后一座城市从「到达时间 + 45 分钟」之后开始；剩下的时间不足 2 小时就不排景点，只留提示。这正是现有排程器对「到达日 / 离开日」已经会做的事（`arrival_time` / `departure_time`），所以每一段直接用它，不用改排程器。
- **页面**：
  - 新建页「行程信息」里多一个「＋ 添加下一座城市」，每段填目的地和开始 / 离开日期；段与段之间填交通方式和时间（没填时放占位并提示，按两城直线距离给一个**估算**的时长，写明「估算」）。
  - 生成后进入「旅行」页：按段分页签（北京 · 3 天 / 西安 · 3 天），中间是移动卡「北京 → 西安 · G87 · 10:00 → 14:35」；点进某一段就是现在的行程页，上面有「第 2 段 / 共 2 段，上一段 / 下一段」。
  - 预算、行李、导出：按段分开，再合计（币种不同按汇率并写明日期）。

## 三、不这样做的原因（对比）

另一种是把一份行程改成「每天一座城市」：数据模型更「纯」，但要改 131 处，而且编辑、预算、导出都要重新验证一遍。这次不选。代价是：**每一段是独立行程，跨段的整体操作（比如把整趟旅行平移几天）要在旅行这一层单独做**，第一版先不做。

## 六、第 1 步的做法与限制（旧做法，已被第八节取代；第 ③ 批删掉了旧的旅行页和 `/trips` 接口，下面写的 `/trips`、旅行页都不再存在）

- 接口：`POST /trips`（旅行设置 → 每段一个后台生成任务，先全部校验再开始）、`GET /trips/{id}`（每段的进度、行程号、换城市的交通）；行程详情多一个 `trip`（第几段、上一段 / 下一段）。代码在 `app/trips.py`，存储是 `trips` / `trip_legs` / `trip_transfers` 三张表。
- 换城市那天两段共用：第一段的返程 = 换城市的交通、第二段的去程 = 同一条交通，排程器按「出发前 / 到达后」各自排，不改排程器。
- 提前量按交通方式：飞机照旧（抵达后 60 分钟、离开前 180 分钟），高铁 / 火车 / 大巴到站后 45 分钟、离开前 90 分钟；离开那天的接驳项写「前往机场 / 车站」，换城市时写「前往车站，去里昂」，不再一律写「前往机场（返程）」（单城市行程坐高铁返程也一样）。
- 没填交通：按两城直线距离估算（超过 800 公里飞机，否则高铁，10:00 出发），页面标「估算」；估算出来当天到不了（隔夜）就拒绝并说明。
- 新建页：点「＋ 添加下一座城市」，每座城市各填目的地、开始日期、离开日期、选主题（默认均衡）；下一座城市默认当天开始，也可以第二天开始（夜车 / 红眼航班），隔两天以上要多加一座城市；第一座城市改离开日期，后面的城市整体平移；换城市的出发 / 到达钟点可填可不填（日期不用填）。
- 每座城市自己的深度路线、必去 / 不去和住宿：第一座城市用表单原来的位置，后面的在各自卡片里；提交时放进该段的 `options`（`route`、`route_stops`、`must_go_ids`、`avoid_ids`、`place_weights`、`stays`），不认识的键丢掉；选了深度路线就不再选主题。
- 旅行页改交通：`PUT /trips/{id}/transfers/{位置}`，两段都生成完才能改；出发日 = 前一座的离开日、到达日 = 后一座的开始日，改的是方式、钟点和车次；两段先都算好、都校验过再保存，各生成一个版本。
- **一页看全程（2026-10-31 你拍板：内部仍是每座城市一份行程）**：旅行页 = 封面（各城市景观图轮播）+ 总览（每座城市一个按钮，点了滚动到那一段）+ 按城市分段的只读日程 + 换城市的交通卡；改某个景点、看地图 / 预算 / 行李仍在每座城市自己的行程页里（每段有「完整行程」入口）。
- **平移 = 整趟平移**：`POST /trips/{id}/shift`；在某一座城市的行程页平移（`POST /plans/{id}/shift`）也走它，所有段和换城市的交通一起动；先全部算好再保存。
- **还没有的**：整趟的合并导出、预算合计、行李合并在第 2 步。

## 七、已确认（2026-10-31）

1. **做法**：几份单城市行程串起来（不改成每天一座城市，那要改 131 处）。
2. **移动日**：上午在前一座城市、下午在后一座城市，剩的时间不够就只留提示。
3. **每段的主题**：每座城市自己选主题，默认「均衡」。

## 八、第 2 版：真正的一份行程（2026-10-31 你要求，**设计已确认；第 ①–⑥ 批都已做完并确认（2026-11-02）**）

你的要求：我的行程里多城市只显示一张卡片；所有城市放进一张行程表，直接在一页里编辑（不是「总览页 + 每座城市另开一页」）。参考 TREK（AGPL，只借思路）和 TripStar-Java：它们都是「一趟旅行 → 一份天列表，每天带地点」，多城市只是每天标一个城市；它们没有我们每座城市的地点库 / 预算 / 行李 / 预约 / 版本这套深度，直接照搬有限。

### 做法：一份行程 + 「逐城市适配层」

- **数据**：一趟多城市旅行 = **一份行程**（一个行程号、一套版本历史、一张卡片）。
  - 请求多一个 `legs`（每座城市的起止日期、主题、路线、必去 / 不去、住宿）和 `transfers`（换城市的交通）；单城市行程这两项都没有，**完全不变**。
  - 行程里每个 `Day` 和每个条目多一个可选的 `city_id`（单城市行程没有）。
  - 换城市那天仍是**一天**：上午是前一座城市的条目，中间是「前往车站，去里昂」，下午是后一座城市的条目；按条目的 `city_id` 分得开。
  - 地点库：多城市行程用一个「合并地点库」（各城市地点库合在一起，地点号不能重复，重复就加城市前缀），现有按地点号查地点的代码不用改。
- **不重写排程器**：现有的单城市排程、编辑、预算、天气、行李、导出都原样保留，新增 `app/multicity.py`，做两件事：
  - `split`：把一份多城市行程按城市拆成几份「单城市视图」（每份有自己的请求和行程，换城市那天各取自己那半天）；
  - `merge`：把各城市的结果合回一份。
  - 每一项操作都是「拆开 → 对对应的城市用现有代码 → 合回去」：质检、预算（各城市分开列再合计）、行李、天气、地图、ICS / PDF（每个事件用所在城市的时区）、编辑（换点 / 拖拽 / 锁定 / 重排 / 住宿：按被改的那一天所在的城市）。整趟平移、改换城市的交通直接改这一份行程的请求。
- **页面**：行程页就是现在的行程页，每天标城市、目录里按城市分段，封面轮播各城市的景观图；「我的行程」里只有一张卡片，标题「巴黎 → 里昂」。现在的旅行页和「上一段 / 下一段」去掉。

### 分三批做（每批做完你验收、你说提交才提交）

| 批 | 内容 |
|---|---|
| ① ⏳ | 数据（`legs` / `transfers` / `city_id`）、拆分与合并、按一份行程生成、读取路径（质检 / 预算 / 天气 / 行李 / 导出）、「我的行程」一张卡片、接口测试 |
| ② | 在一页里编辑：换点、拖拽、锁定、重排、住宿、整趟平移、改换城市的交通、版本对比与回滚 |
| ③ ⏳ | 页面：每天标城市、按城市的目录和封面轮播、新建页直接生成一份；把你现在已有的两份行程（上海 + 重庆）合并成一份（一次性脚本），删掉旧的旅行页 |

### 风险（先说清楚）

- 换城市那天的拆分 / 合并是最容易出错的地方，会有专门的测试（上午 / 下午各一半、夜车、只待一天的中间城市）。
- 多城市行程里，用大模型改写（「帮我把第二天换成……」）按那一天所在的城市处理，跨城市的一句话改动先不支持（会提示拆成两句）。
