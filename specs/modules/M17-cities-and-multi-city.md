## 为什么

现在产品只认巴黎：`app/` 里有 27 个文件直接写了巴黎（地点库、`Zone.paris`、`price_eur`、日历时区、`SUPPORTED_DESTINATIONS`、提示词……）。要支持国内城市和「一趟旅行去好几个城市」，先要把「城市」变成一份配置和一套数据，再谈多城市。

## 你已拍板的取舍（2026-10-22）

- 第一个国内城市：**北京**。第二个：**西安**（我的默认：北京 → 西安有高铁，是最常见的组合；K1 开始前你可以改）。
- 数据深度：两个城市**各约 35 个点、3–4 个主题**，只覆盖最热门的点；每个点都带核对记录。巴黎仍是 81 个点。
- 国内天气**继续用 Open-Meteo**（免费、不要 Key、能看 15 天、有「去年同期」兜底；高德天气只有 3 天预报，个人认证每月仅 5000 次）。
- 范围：做 GPX 导出 + KML / GPX / KMZ 导入、航班 / 火车手填多段。**不做**：Google 地图列表导入、订单确认邮件解析、视口 POI 探索；代理只在 README 写明怎么用环境变量走代理。
- 事实仍只信策展数据：高德只做地图、搜索、路线，不当事实来源；高德返回的数据不进地点库。

## 目录结构

- `data/cities/<id>.json`：城市配置（见 S1）。现有数据文件位置不动（`data/places/<id>.json`、`data/themes/<id>.json`、`data/budget/<id>.json`、`data/companion/`、`data/places/media.json` 按城市分块）。
- `app/cities.py`：`City`、`load_city(id)`、`list_cities()`、`city_of(destination_text)`。其余模块不再出现城市字面量，一律从 `City` 取。
- 新数据文件：`data/cities/city-pairs.json`（城际参考时长，带官方来源）、`data/transport/airports.json`（K5，只收已支持城市的机场）。

## 验收场景

**S1 P0 · 城市是一份配置（K0）**
- 假设 开发者新增一座城市
- 那么 只需要新增 `data/cities/<id>.json` 和这座城市的地点 / 主题 / 预算数据，不改任何代码字面量
- 配置项：`id`、`name_zh`、`name_en`、`aliases`（「北京」「beijing」……）、`country`、`currency`（`EUR` / `CNY`）、`timezone`、`center`、`bbox`（超出范围的地点必须标 `day_trip`）、`coord_system`（库里一律 `wgs84`）、`map_provider`（`osm` / `amap`）、`zones`（`core` / `day_trip`）、`residency_options`（出行人身份选项，欧洲城市保留「长居欧盟 / 法国」，国内城市没有）
- 地点库的 `zone` 从写死的 `paris` 改成 `core`；老数据文件加载时自动把 `paris` 读作 `core`，不用改 81 条数据

**S2 P0 · 巴黎行为完全不变（K0 的底线，已用 `tests/test_k0_paris_baseline.py` 固定）**
- 假设 K0 做完
- 那么 同一份固定请求（同样的日期、主题、人数、预算）生成的行程 JSON、预算、PDF、ICS、KML 与 K0 之前**逐字一致**；已有的单元测试和浏览器验收一条不改、全部通过
- 并且 巴黎行程的 ICS 时区来自 `City.timezone`，仍是 `Europe/Paris`；天气中心来自 `City.center`

**S3 P0 · 首页能选城市（K1）**
- 假设 我打开首页
- 那么「你想去哪里」下面能选城市（巴黎 / 北京 / 西安）；选定后主题列表、地点、币种、出行人身份选项都换成这个城市的
- 并且 一句话填表里写「十月去北京玩 4 天」会选中北京；写了没有支持的城市（东京）仍提示「目前只支持 …」，列出已支持的城市
- 并且 每个行程按城市取数据：行程页标题、封面大图、ICS 时区、天气、日落、抵达文案（「抵达巴黎并前往住宿」里的城市名）都跟着城市走；老行程当巴黎

**S4 P0 · 国内价格用人民币，不换汇（K1）**
- 假设 我生成北京的行程
- 那么 门票、预算都是人民币，预算页没有「汇率」行，结算币种不再出现「欧元并列」；没有价格的点标「待补」，不编数字
- 并且 优惠规则按官方写法录入：学生票、60 岁以上、未成年人、军人 / 残疾人等；系统只按出行人的**年龄和学生身份**判断，**身高类**（「1.2 米以下免票」）在预算里标「以现场身高为准」，不假装精确
- 并且 出行人表单里没有「长居欧盟」这类选项（`residency_options` 为空就不显示）

**S5 P0 · 预约渠道，不只是官网链接（K1）**
- 假设 北京故宫要在官方预约平台实名预约，颐和园可以现场买票
- 那么 地点带 `booking_channels`：`kind`（`website` / `wechat_official` / `mini_program` / `app` / `phone` / `on_site`）、名称、链接（有才有）、核对日期、来源；预订清单显示渠道名称和是否**实名**（`real_name_required`），没有官网链接的写公众号 / 小程序名称，**不编网址**
- 并且 「永远不信模型给的网址」不变：`official_url` 和渠道链接只来自策展数据

**S6 P0 · 国内数据闸门（K1）**
- 假设 开发者新增或修改国内地点
- 那么 完整性测试要求：闭馆日、价格（含优惠）、预约渠道、坐标各有**来源 + 核对日期**；坐标至少两个来源交叉（OSM / 维基数据 / 官方）且相差 ≤ 150 米；官方链接能打开且域名属于官方；`bbox` 之外的点必须标 `day_trip`；人民币价格不得写进 `price_eur`
- 并且 核对脚本沿用 `scripts/` 里巴黎那一套，不一条条手填

**S7 P1 · 北京 / 西安数据覆盖（K1）**
- 北京约 35 点：故宫、天坛、颐和园、国家博物馆、八达岭长城（`day_trip`）、胡同与美食街区、公园等；西安约 35 点：兵马俑（`day_trip`）、城墙、陕西历史博物馆、回民街等。**具体名单在 K1 开始时给你过目**，核对不过的点不收。
- 主题 3–4 个（古迹、博物馆、美食与街区、自然 / 公园），每城一份；随行清单按城市和季节（北方冬天、夏天暴雨……）有对应的条目

**S8 P0 · 多城市：城市段与城际移动日（K3）**
- 假设 我建一趟「北京 3 天 → 西安 3 天」的行程，中间是高铁
- 那么 行程由有序的**城市段**组成（`legs`：`city_id`、起止日期、住宿区），段与段之间是一条**交通段**（M06 S6：方式、出发 / 到达地、出发 / 到达时间、车次、确认码），没写时系统放一条占位并提示「请填写实际车次和时间」，用 `city-pairs.json` 里的参考时长（带官方来源）估算
- 并且 **移动日**那天：出发城市的景点排在「出发时间 − 到站 / 到机场提前量」之前（高铁 90 分钟、飞机 150 分钟）；到达城市的景点排在「到达时间 + 45 分钟」之后；剩下的时间不足 2 小时就不排景点，只留提示；当天不再排午餐之外的跨城安排
- 并且 每一天都属于某个城市：该天的地点、天气、主题、开放时间按这座城市算；单城市行程完全不变（`legs` 缺省 = 一段）
- 限制：最多 8 个城市段（`MAX_LEGS`；原先是 3，后来放宽到 8），每段自己的开始 / 离开日期（可以只待一天；下一座在上一座离开的当天或第二天开始），整趟至少 2 天，每段最多 14 天，超出给出提示（沿用「第一版建议」的做法）

**S9 P1 · 多城市行程在页面上的样子（K3）**
- 假设 我打开一趟两城行程
- 那么 日程中间有一张「北京 → 西安 · G87 · 10:00 → 14:35」的移动卡；「全程地图」按城市分页签（两座城市隔着上千公里、供应商也可能不同，不画在同一张图上）；统计小卡片的公里数只算各城市内的路程，不含城际
- 并且 预算按每个城市段分开列，再合计；币种不同时按已有的汇率规则换算并写明汇率日期
- 并且 PDF / 长图 / ICS / KML / GPX 按天分城市：ICS 每个事件用所在城市的时区，移动日的交通事件带出发和到达两个时区；分享页同样显示
- 并且 编辑、平移日期、复制、回滚、版本对比对多城市行程都正常；平移是整体平移所有城市段和交通段；在某一天里换点只能从**这一天所在城市**的地点库里换

**S10 P1 · 候选池与必去 / 不去（K3）**
- 假设 我在一趟两城行程里写「必去：故宫、兵马俑」
- 那么 每个名字按所有城市段的地点库匹配，归到对应城市段；匹配不到的进「没找到」；候选池按城市分组；主题在某城市没有对应的包时，提示并退回该城市的默认主题

**S11 P0 · 不会把国内城市排错（K1–K3 的共同底线）**
- 假设 北京故宫周一闭馆
- 那么 排程器和质检用同一套闭馆日规则（和巴黎一样）：周一不排故宫；用户「必去」硬要去时给出明确提示；长期闭馆、预约要求同样在预订清单里出现

## 数据与接口

- `GET /cities`（K0 已做）：已支持的城市列表（`id`、中英文名、国家、币种、时区、中心点、`map_provider`、`residency_options`）。`/themes`、`/places`、`/places/search`、`/places/{id}`、`/attractions`、`POST /intake/nl` 都带可选的 `city`（缺省 `paris`）；不认识的城市 404，并列出现在支持哪些。
- 行程的城市（K0 已做）：`TravelRequest.city_id` / `.city` 是**只读属性**，按 `destination` 认出来（「Paris」「巴黎」→ paris），所以请求 JSON、存下来的老行程、所有接口的输出都没有多出字段，老行程自然就是巴黎。显式的 `city_id` 字段随 Q2 的新建页（用户选城市）加，`legs[]` / `transfers[]` 随 K3 加；响应里 `trip.legs`、每天的 `city_id` 也随 K3。
- SQLite：K0 **不动数据库**（城市从 destination 认）；显式 `city_id` / `legs` 进需求 JSON 时再决定要不要升 schema。
- 币种：`Place.price` 用所在城市的币种，`price_eur` 在巴黎数据里保留并兼容读取（K0 的数据迁移不动 81 条原文，只在加载时映射）。

## 验收方式

- **自动化**：城市配置完整性（每个城市必填项、`bbox`、币种与价格字段匹配）；巴黎回归快照（S2：固定请求下 JSON / 预算 / ICS 一致）；国内数据闸门（S6）；移动日窗口计算（提前量、不足 2 小时不排）；`legs` 校验（段数、天数、连续性）；平移 / 复制 / 回滚对多城市行程的行为。
- **评测**：北京、西安各 3 份固定请求，行程里不出现闭馆日冲突、必去全落地、预约要求全部出现在清单里。
- **前端**：你按 S3、S4、S5、S8、S9 点一遍；Playwright 断言：首页城市切换、人民币无汇率行、移动卡、分城市页签、ICS 事件时区。
