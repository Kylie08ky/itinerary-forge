# M07 质检与可信度

> 版本：持续演进。v0.1 保持并扩充 → v0.2（解释、调用追踪）→ v0.3（LLM Judge）
> 功能：F41 F42 F43 F44 F45 F46 · 来源：自有（这是三个项目里只有我们才有的部分）

## 为什么

这是我们和 TREK、TripStar 的差异点：它们帮你排，但不会告诉你「这份行程哪里有问题」。我们要做到：**能自动发现问题，能解释，能证明事实是可信的**。

## 范围

做：确定性规则（持续增加）、事实核对状态、LLM Judge、回归与评测、排程解释、LLM 调用追踪。
不做：替用户做最终判断；所有质检结论都给出理由和位置。

## 用户故事

- 作为游客，我想一眼知道这份行程能不能直接拿去用。
- 作为游客，我想点开每条问题，看到是哪一天哪一项、为什么。
- 作为开发者，我想改了规则后，能确认没有把以前正确的判断改坏。

## 验收场景

**S1 P0 · 质检徽标与问题清单（已有，保持）**
- 假设 行程里有一个活动早于抵达时间
- 那么 徽标显示「1 error · 待人工处理」，下方列出「第 1 天：抵达日首个安排早于抵达时间 + 缓冲」，点击定位到该条目

**S2 P0 · 长期闭馆被拦截**
- 假设 我手动把蓬皮杜中心加进某天
- 那么 立即出现 error「该馆长期闭馆」，并说明依据（策展数据的备注与核对日期）

**S3 P0 · 编辑后自动重检**
- 假设 我拖拽了一个点
- 那么 徽标和问题清单在 1 秒内刷新

**S4 P1 · 为什么这样排**
- 假设 我点开某天的「为什么这样排」
- 那么 看到选点理由、顺序理由（见 M03 S9）

**S5 P1 · LLM Judge 主题契合度（开发者评测工具，不在产品界面里）**
- **你验收后的决定**：评估主题契合度对用户没用——用户不需要看一个模型打的分，产品本身应该直接符合用户的需求。所以**行程页没有评估按钮、没有分数、没有接口、不存库**（批次 G 里做过的按钮和接口已撤掉；做过又撤的 v12 库表 `judge_results` 会在启动时自动删除）。
- **留下来的**：`app/judge.py`（评委：只看主题名 + 定位 + 每天每个安排的开始时间、名称、类别、室内 / 室外和最佳时段（不给价格 / 开放时间），给 1–5 分 + 一句理由；返回不合规重试 1 次；模型不可用抛错）和 `scripts/eval_judge.py` + `tests/evals` 思路——给**开发者**评测「排程算法生成的行程，是否真的围绕所选主题」，用来改选点规则和主题配方，从源头让产品符合需求。
- **评测怎么做**：每个主题造三种固定用例——「对得上」（这个主题生成的行程，拿这个主题评）、「冒充」（用成员地点重合最少的主题生成的行程来冒充，应该低分）、「近邻冒充」（用重合最多的主题生成的行程来冒充，比如艺术 vs 博物馆，应该比「对得上」低；这两个主题本来就重叠，所以只要求「对得上 ≥ 近邻」，不要求低于 3 分）。默认每个用例跑 3 次，统计各类平均分和最低 / 最高（看稳不稳）、「对得上 > 冒充」「对得上 > 近邻」的主题数、高低分组的阈值比例；另外不用模型算一个「成员占比」做对照；分数不理想的用例打印模型给的理由。需要本地 Ollama，**没开时跳过**（退出码 0）；换模型 / 改提示词后重跑对比。
- **自动化**：`tests/test_judge.py`（解析与容错、提示词只含主题和行程项、产品里没有评估接口、生成时不调评委）、`tests/test_eval_judge.py`（用例构造和统计，用假评委）。真模型的判断力不在单元测试里测。
- **以后**：如果评测发现某个主题的行程总是和主题对不上，就去改地点库的主题成员 / 配方，再重跑评测确认变好，而不是把分数给用户看。
- **评测记录**（`qwen2.5:7b-instruct`，24 个用例 × 3 次，2026-10-21）：
  - 第一次（2 类用例 × 1 次）：对得上 4.0 / 冒充 1.88，8/8 分得开；摄影只有 3.0。
  - 加上「近邻冒充」和 3 次重复后发现两个真问题，都是**产品问题**，不是评委偏了：① 摄影 / 美食 / 娱乐的行程里借来了百货商店等不搭的小点（M03 S11）；② 摄影行程里没有黄昏时段的点，排程的「黄昏最佳」是固定的 16:30（M03 S12）。另外评委当时看不到时间，补上开始时间和室内 / 室外后才能判断光线类主题。
  - 修了之后：对得上平均 **3.88 → 4.46**，对得上 ≥ 3 分 21/24 → **24/24**，对得上 > 冒充 7/8 → **8/8**；摄影 **2.0 → 4.0**。「近邻冒充」对得上 > 近邻 6/8：剩下的两个是艺术 vs 博物馆（成员重合 36%，本来就几乎一样，模型都给 4–5 分），不算评委的问题。

**S6 P1 · 任务轨迹与模型用量（v0.2 已做）**
- 假设 一次生成花了 40 秒
- 那么 行程页「生成过程（耗时与模型调用）」展开后看到：每一步耗时、模型调用次数 / 失败次数 / token / 费用，每次调用的用途、模型、耗时、成败；降级时写明原因（如「模型不可用，说明文字由模板生成」）
- 并且 「我的行程」页的「模型用量」页汇总所有调用：总次数、失败数、平均耗时、token、费用，按用途分组（写每天的说明 / 理解一句话修改 / 自由生成），外加最近的调用
- 并且 只记次数、耗时、字数、token 和成败，**不保存提示词和模型返回的原文**（里面有用户的原话）
- 并且 本地模型费用为 0；换付费模型时在 `.env` 里填 `LLM_PRICE_IN_PER_MTOK` / `LLM_PRICE_OUT_PER_MTOK`（每百万 token 美元价）就会自动统计
- 注：同步接口生成的行程没有任务，展开后提示「没有生成轨迹」；记录失败不会影响真正的模型调用

**S7 P0 · 回归集守护**
- 假设 开发者修改了某条规则
- 那么 回归测试在冻结用例上比较前后输出，任何不在预期内的变化都会让测试失败

## 规则清单（现有 17 条 + 计划新增）

现有：天数、日期、时间格式、顺序、时长、交通、日强度、时段覆盖、必去、重复景点、避开、预约清单、抵达 / 离开缓冲、闭馆日、长期闭馆、画像一致、目的地一致。
计划新增（v0.1–v0.2）：开放时间冲突、通勤超过阈值、同一天跨区过多、预约点时段冲突、郊区点同天并存、午晚餐缺失、住宿首尾不连贯。

## 数据与接口

- `Finding{code, severity, message, day, item_index, evidence}`，新增 `evidence`（依据与核对日期）。
- 接口：`GET /trips/{id}/report`、`GET /tasks/{id}/trace`、`GET /plans/{id}/trace`（凭行程号找到生成它的任务）、`GET /llm/usage`。
- 存储：SQLite 的 `llm_calls` 表（schema v4）；`TracedClient` 包在任意 `LLMClient` 外面，用途和任务号靠 contextvar 传递。

## 验收方式

- **自动化**：每条规则正反各至少一个用例；回归集；`evidence` 必填的断言。
- **评测**：LLM Judge 与人工打分的一致性（用你手动标注的 20 份行程）。
- **前端**：你按 S1、S2 点。
