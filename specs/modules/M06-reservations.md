# M06 预约与订票

> 版本：v0.1（清单 + 官网链接）→ v0.3（预订记录、最晚订票、住宿）→ v0.5（航班 / 火车手填多段；邮件导入推后）
> 功能：F35 F36 F37 F38 F39 F40 · 来源：自有 + TripStar（预约提醒）+ TREK（预订）
> **现状（2026-10-28）**：✅ 已做完：购票清单（三档 + 官网链接 + 最晚订票）、预订记录、住宿（跨天、每天锚点、住哪个区推荐）。航班 / 火车多段、机场库（v0.5 K3 / K5）暂缓，邮件导入推后。

## 为什么

前提是用户**自己**登录官网订票。所以产品的任务是：告诉你哪些要订、最晚什么时候订、去哪订，订完记下确认码。

## 范围

做：预约清单、官网链接、最晚订票日、预订状态与确认码、附件、住宿跨天。
后做：航班 / 火车多段、订单邮件 / PDF 导入。
待你拍板：AirTrail 联动（F40，建议不做）。
不做：代订、支付。

## 用户故事

- 作为游客，我想看到一张「必须提前订」的清单，每项能点开官网。
- 作为游客，我想知道最晚什么时候订，快到了要提醒我。
- 作为游客，我想订完后把确认码和截图记在行程里。

## 验收场景

**S1 P0 · 预约清单与官网链接**
- 假设 行程包含卢浮宫（必须线上）、凡尔赛宫（线上或现场）
- 那么 页面分两组：「必须线上购票」里有卢浮宫、「建议线上购票」里有凡尔赛宫，每项显示原因和「官网购票」链接，链接是地点库里核对过的官网

**购票方式分三档（你的决定）**：规则是「有线上购票渠道就推荐线上购票；除非你说想收集纸质票根」。

| 档位 | 页面上写什么 | 官网购票链接 |
|---|---|---|
| 必须提前线上购票 | 红色标签「必须提前线上购票」，进「必须线上购票」清单 | 有 |
| 线上购票，现场也可排队 | 标签「建议线上购票 · 现场也可排队」，进「建议线上购票」清单 | 有 |
| 无需购票 / 免费 | 不出现购票标签 | **没有，只给地址** |

- 拿不准的按「必须线上」处理：误报「现场能买」的代价（到了进不去）比误报「必须线上」大。
- 有购票说明（如「奥赛 2026 年起须订时段，官方说法不一」）的写在地点旁，并写明哪天查的、资料来源是第三方，以官网为准。
- 现场排队多久、热门景点现场不一定有票这类经验，**以后参考小红书笔记补充**（见 M12），现在不编。

**S1b P0 · 三档的显示**
- 假设 行程里有卢浮宫（必须线上）、罗丹博物馆（线上或现场）、杜乐丽花园（无需购票）
- 那么 卢浮宫标「必须提前线上购票」并有官网链接；罗丹标「建议线上购票 · 现场也可排队」并有官网链接；杜乐丽花园没有购票标签、没有链接，只有地址；PDF / Markdown 导出同理

**S1c P1 · 想收集纸质票根**
- 假设 我在首页勾选了「想收集纸质票根」
- 那么 「现场也可排队」档的地点，清单里改写成「到现场窗口排队购买即可」；「必须线上」档的地点写「只能线上购票，纸质票根不一定能拿到」；不勾选时一律推荐线上购票

**S2 P0 · 链接绝不来自模型**
- 假设 模型在输出里写了一个看起来像官网的地址
- 那么 页面展示的永远是地点库的官网；地点库没有官网的项只显示「请自行搜索官网」，不显示任何链接

**S3 P1 · 最晚订票日（v0.3）**
- 假设 卢浮宫的订票建议是「提前 1–2 周」，参观日是 10-04
- 那么 清单显示「建议最晚 9-20 前订（经验值：提前 14 天，非官方规定）」；距今不足时显示红色「马上订」，还剩 ≤3 天显示橙色「快到了」，已订的不提醒
- 只有**地点库里有明确提前量的地点**才给日期：卢浮宫（14 天）、圣礼拜堂（7 天）、塞纳河游船（7 天）、迪士尼（7 天）、红磨坊（30 天）。其余（含埃菲尔铁塔「旺季提前数周」这类没有明确天数的）只显示「建议尽早」，**不编数字**
- 提前量的依据是地点库里该地点的订票说明（来源多为第三方经验，页面上写明「经验值，非官方规定」）；官网有明确规定时以官网为准
- 一个地点在多天出现时，按最早的一天算

**S4 P1 · 勾选「已订」→ 填入馆时间 → 行程自动锁定（v0.3；截图随 v0.4 文件附件）**
- 假设 我订完了卢浮宫，入场时间是 10:00
- 当 我在购票清单里**勾上这一项前面的框**（表示已订好），下面出现「入馆时间」输入，我填 10:00
- 那么 对应景点在行程里被**锁定在 10:00**（带 🔒），当天其他安排自动围绕它重排，并生成一个新版本（标「预订锁定」，摘要「预订：卢浮宫 10:00 入场，已锁定」）
- 当 门票是**一个时间段**进场（比如 10:00–10:30 之间入场）
- 那么 我填「入馆时间」= 10:00、「时段结束」= 10:30；系统把景点排在这个时段内：它原来的开始时间就在时段里就保持不变（只加锁），早于时段就移到时段开始，晚于时段就移到时段结束
- 当 我取消勾选，或清空入馆时间
- 那么 由预订加上的锁解开（再生成一个「取消预订」版本，时间保持不动，下次重新排程才会变）；确认码、备注保留
- 并且 勾选后还可以填确认码、备注；清单项变绿显示「已订 ✓」；PDF 里也带上确认码和入场时间；刷新、换设备打开仍在
- 并且 只勾选、不填入馆时间也行：只是标记已订，不动行程
- 并且 当天排不下 / 赶不上这个时间，页面提示说明原因，预订记录照存
- 并且 勾选本身、确认码、备注不产生行程版本（只有「填了入馆时间 → 锁定行程」才产生）；**公开分享页不显示确认码**
- 并且 如果之后平移了日期、换了天数，导致这个地点的参观日和我订票时记下的不一样，清单项提示「行程日期变了：这笔预订是为 X 日订的」
- 并且 状态可改回「未订」；确认码最多 60 个字符；地点必须是需要订票的（无需订票的地点不能记预订）

**S5 P1 · 住宿跨天并作每天锚点（v0.3）**
- 假设 我添加住宿，入住 10-03、退房 10-06
- 那么 10-03 到 10-05 每天的顶部都显示「今晚住：这家酒店」，退房那天显示「退房：这家酒店」；重新排程时它是每天路线的起终点
- 住宿存在每个版本自带的需求里（`stays`）：平移日期会一起顺延、回滚会一起回到那一版、复制会一起带走；保存住宿会生成一个「住宿更新」版本（行程内容不变，除非勾选「按新住宿重新排程」）
- 每家住宿填：名称（必填）、入住 / 退房日期、所在区或地址（至少一个）、每晚价格（选填，欧元，给预算用）、备注
- 日期必须在行程日期范围内、退房晚于入住、两家不能重叠；不满足时说清楚哪里不对
- 有地址时尝试用 OpenStreetMap（Nominatim，免费、不需要 Key）定位到坐标；定位不到就用所在区的中心，页面上写明「按 X 区中心估算」，不假装精确
- 酒店名、地址是你填的，不是策展数据；系统不推荐具体酒店、不编价格

**S5b P1 · 住哪个区（v0.3，F17）**
- 假设 我还没订酒店，点住宿卡片里的「住哪个区？」
- 那么 给 2–3 个备选区（按行程里各景点的位置，算住在哪个区到各景点平均直线距离最短），每个写明理由：「到行程里 N 个景点平均 X 公里，其中 M 个在 2 公里内」；点一个就填进住宿表单的「所在区」
- 并且 写明局限：只按景点位置算，不含酒店价格、治安、噪音、交通换乘便利度；郊区景点（凡尔赛、迪士尼）不参与计算；区的中心用该区已收录景点的位置近似
- 并且 行程里没有景点时不推荐，提示「先生成行程」

**S6 P1 · 交通段：航班 / 火车 / 大巴手填多段（v0.5 K3，K5 补航班）**
- 假设 我在行程页的「预订」里点「添加交通」，选「火车」，填：出发站、到达站、出发时间、到达时间、车次、确认码（选填）、备注
- 那么 这一段成为一条**交通段**，出现在对应日期的日程里（移动卡：「北京 → 西安 · G87 · 10:00 → 14:35」），并写进预订清单的「交通」栏；多个城市段之间的城际交通就是交通段（见 M17 S8）
- 并且 方式有：火车 / 航班 / 大巴 / 自驾 / 轮渡；一次出行可以有多段（中转航班就是两段，到达与下一段出发之间显示换乘时间，不足提醒）
- 并且 时间都是**当地时间**，每一端带时区（默认取所在城市的时区，可在常用时区里改）；到达早于出发（时区不同）按时区换算后判断，不允许到达早于出发；PDF / 长图 / ICS 里按各自时区显示（K5：ICS 事件带出发和到达两个时区）
- 并且 K5：机场库（`data/transport/airports.json`，只收已支持城市的机场，带来源）自动填机场所在城市和时区；首页的「抵达 / 离开时间」可以由第一段 / 最后一段航班联动填入
- 并且 **不抓 12306 或机票接口**，车次、时间都是你填的，系统不推荐车次、不编票价；没填时系统只给一条带官方来源的参考时长占位，并提示「请填写实际车次和时间」
- 并且 交通段随行程复制 / 平移（整体顺延）/ 回滚；公开分享页和长图不显示确认码

**S7 · 订单邮件导入（推后）**
- 你 2026-10-22 拍板：推到 v0.5 之后（范围大、涉及隐私面广）。需要时用本地模型解析，不用 KItinerary。

## 数据与接口

- 实体：`Reservation`（见 [03](../03-data-model.md)）；`book_by` 由参观日和地点库的 `lead_time_hint` 计算。
- 接口（沿用 plans 命名）：`GET /plans/{id}/reservations`（清单 + 预订状态 + 最晚订票日）、`PUT|DELETE /plans/{id}/reservations/{place_id}`；`GET /plans/{id}/stay-recommendation`；`PUT /plans/{id}/stays`（整体替换住宿列表，可选重新排程，生成新版本）。附件接口随 v0.4。
- 预订记录存在 SQLite 的 `reservations` 表（schema v7），按（行程号，地点 id）唯一；复制行程时一起复制，删除行程时一起删除。
- 地点库 `Booking.lead_days`：明确的提前订票天数（只对上面五个地点填），必须有订票说明作依据（完整性测试）。

## 验收方式

- **自动化**：`book_by` 计算；任何响应中的 `url` 必须出自地点库（属性测试）；预订状态流转。
- **前端**：你按 S1、S3、S4 点；Playwright 断言链接 `href`。
