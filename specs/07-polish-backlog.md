## 二、清单

### 入口与导航（Q2，你 2026-10-23 拍板：首页英雄图按下面的规则轮换；我的行程卡片封面用城市大图）

**三个页面各管一件事**：`/` 首页（入口）、`/new` 新建行程（纯表单）、`/plans` 我的行程。导航里「新建行程」去 `/new`，品牌图标回 `/`。手机底部标签栏的第一个是「首页」（回 `/`），后面是新建 / 我的行程 /（进行中才有的）今天 / 用量；在 `/new` 时高亮的是「新建」。

**P01 普适首页（`/`）**
- 现状：`/` 就是「巴黎的新建行程」，英雄图、标题、表单都是巴黎的。
- 目标：首页是整个产品的入口，不绑定任何城市：
  - 全屏英雄图：**有下一站（最近一个还没结束的行程）时用那座城市的标志性大图；没有行程时，轮换各已支持城市的标志性大图**（按日期轮，同一天内不变；现在只有巴黎，所以先只会是巴黎）。大图没有 / 加载失败 → 城市主色渐变。
  - 标题「你想去哪里？」+ 一句话输入卡 + 「导入笔记」按钮；去掉「PARIS · ITINERARY」这类写死城市的字样（小标签改成不带城市的「ITINERARY」）。
  - 英雄下面：下一站倒计时（P02）、「即将出发」最多 3 张行程卡（P03 的卡片）+「全部行程 →」；**已支持的城市多于一个时**才显示「城市入口」（点一个去 `/new` 并选好这座城市）。没有任何行程时，英雄下面不放东西。
- 数据：`GET /cities` 每个城市带 `hero`（该城标志性大图的署名信息）；城市配置里的 `landmarks` 给出「标志性」的优先顺序。
- 前端：打开 `/`，除非有巴黎的行程，页面上没有「巴黎」「Paris」字样；英雄图带署名。

**P02 下一站倒计时放首页**
- 现状：倒计时卡片在 `HomePage` 里和表单混在一起。
- 目标：首页显示**距离现在最近的一个行程**：未出发 → 天 / 时 / 分 / 秒倒计时；进行中 → 沿用「今天」卡片（正在进行 / 下一站 / 导航）；没有即将到来或进行中的行程 → 不显示。
- 前端：有两个未来行程时只显示更近的那个。

**P03 我的行程：卡片封面是倒计时，用城市大图**
- 目标：每张行程卡的封面是**这趟行程里标志性地点的大图**（和行程页封面同一张），压暗一层，叠上倒计时：未出发「还有 N 天」（明天 =「明天出发」，今天 =「今天出发」）、进行中「进行中 · 第 N 天」、已结束「已结束 N 天前」；左下角仍是「N 天」小标签。没有大图的行程退回城市主色渐变 + 主题图标。
- 数据：`GET /plan-cards` 每张卡带 `city_id` 和 `hero`（大图的 `url / author / license`，没有则 null）；选图规则：这趟行程里按城市配置的 `landmarks` 顺序第一个有大图的点。
- 并且 卡片上**不再显示「质检通过」「模板说明」这类给开发者看的标签**；有错误 / 警告时才显示「N 条提醒」。

**P04 首页和新建行程分成两个页面**
- 现状：首页顶部是一句话输入，下面连着整张表单。
- 目标：首页只有输入框和入口；写完一句话点「开始规划」→ 跳到独立的 `/new` 页，**带着这句话自动解析并预填**，并显示「我是这样理解的」；点「导入笔记」→ 跳到 `/new` 并打开导入弹窗；不写一句话、直接点导航里的「新建」也到 `/new`。`/new` 是纯表单页（没有英雄大图，顶部有一张同样的一句话填表卡，写了也能填）。不会自动生成，仍由你确认后点「生成行程」。
- 前端：首页写一句话 → 跳转后表单已填好；浏览器后退回首页；直接打开 `/new` 是空白（默认值）表单。

**P05 我的行程分「即将到来 / 已结束」并按时间排序**
- 目标：分三块：「即将到来」（含进行中，进行中的排最前）按出发日期从近到远；「已结束」按出发日期从新到旧，默认只展开最近 6 条、其余折叠在「更多已结束的行程」里；归档仍是原来的开关。「今天」按本机日期算。
- 前端：三条不同日期的行程，顺序和分组与上面一致。

### 新建行程（Q3，Q5）

**P06 不只是短途 + 旅行时长建议**
- 现状：表单硬性要求 2–5 天（超出直接报错，不能提交）；一句话填表也只建议 2–5 天。
- 目标：去掉硬限制，改成**软提示 + 时长建议**：选目的地后显示建议，规则来自策展的一张小表（带依据，不靠模型编）——「国内一座城市：2–7 天」「一个国家（多城市）：约 7 天」「多个国家（如欧洲）：10–15 天」；巴黎本身给「4–6 天」并说明为什么（景点密度、日均主要点数）。超出建议范围的天数照样能生成，只提示「这个天数下行程质量可能下降」。
- 范围：**Q3 只做建议和放开限制（到 7 天内保证质量）；8 天及以上的排程质量在 Q5 量过再决定**，更长的旅行靠 K3 多城市。
- 前端：把天数改成 8，能提交、旁边有提示；改成 4，提示「建议 4–6 天」。

**P07 来回交通（必填）+ 生成后的提醒（你 2026-10-23 拍板：交通是必填项）**
- 现状：表单里是「抵达时间 / 离开时间」两个时间框。
- 目标：行程信息只填**开始日期、离开日期**（开始日期 = 你到达目的地的那天，离开日期 = 你离开的那天）；下面一栏「来回交通」**必填**，去程 / 返程各一条：
  - **去程必填**：方式（飞机 / 高铁 / 火车 / 大巴 / 自驾 / 其他）、出发时间、到达时间（到达时间必须在开始日期当天）。选填：出发地、航班号 / 车次。
  - **返程必填**：方式、出发时间（必须在离开日期当天）。选填：到达时间、目的地、航班号 / 车次。
  - 行程第一天按「到达时间 + 缓冲」排，最后一天按「出发时间 − 到站 / 到机场的提前量」排；不再有「默认抵达 10:00、离开 18:00」的假设。
- 并且 生成后出现提醒（进「随行 → 待办」，带紧急度）：**飞机** → 去程 / 返程各一条「网上值机」，截止日 = 起飞前一天，文案「多数航空公司在起飞前 24–48 小时开放网上值机，以你的航司为准」；**高铁 / 火车** → 「取票、提前到站」，截止日 = 出发当天，文案「建议提前约 1 小时到站，带好证件」（通用建议，不编具体规定）；**大巴 / 自驾 / 其他** → 没有。原来不管什么交通都出现的通用「网上值机」待办，在有交通信息的行程里改成上面这样；没有交通信息的老行程保持原样。
- 数据：这就是 M06 S6 的**交通段**，K3 的城际移动日直接复用，不再造第二套。
- 前端：不填交通点「生成行程」→ 提示「请填写去程和返程的交通」并定位到那一栏；选「飞机」填好时间 → 生成后待办里有两条值机提醒；选「高铁」→ 有取票提醒；选「自驾」→ 没有。
- 校验：到达时间要晚于出发时间；去程到达在开始日期、返程出发在离开日期，否则指出哪里对不上。

**P08 住宿（选填）在生成前就能填，且可以多处**
- 现状：表单里只有一个「住宿区域」文字框；住宿要生成后到「住宿」卡里补。后端其实早就支持多段住宿（`stays`，每天锚点）。
- 目标：新建页有「住宿」一栏，**可以加多条**：名称 / 所在区或地址 / 入住日期 / 退房日期 / 每晚价格（都选填，规则同 M06 S5：日期在行程内、不重叠）；不填 = 现在的默认。原来的「住宿区域」并入第一条。生成时用它们作每天路线的起终点和预算。
- 前端：加两条住宿（前 2 晚、后 1 晚），生成后每天顶部的「今晚住」对得上，预算里有住宿一项。

**P09 出行人的填法参考订火车票网站（你 2026-10-23 拍板：姓名要保存）**
- 现状：一行一个人：年龄、居住地、学生。
- 目标：每位出行人一张小卡：**姓名**、年龄、**身份**（成人 / 学生 / 儿童 / 老人，儿童和老人按年龄自动建议）、是否长居欧盟 / 法国（只在目的地有这类优惠时出现，国内城市不出现）、是否欧盟学生（只在适用时出现）；可「添加出行人」「删除」「复制上一位」。
- **姓名保存**：随行程保存（存在这份行程的需求里），预算和预订里用名字称呼（「小明 · 8 岁 省 €xx」），不填就叫「出行人 N」；**「常用出行人」**存在这台设备的浏览器里，下次新建行程一键选。姓名和年龄一样，**不进分享页、长图、PDF、GPX / KML 导出**。**不收证件号、手机号**（我们不订票，不需要，也不该存）。
- 前端：加 3 个人（1 成人、1 欧盟学生、1 小孩，都填姓名）→ 预算里的门票按各自规则算、优惠那行用的是名字；刷新后「常用出行人」还在；分享页和 PDF 里没有名字。

**P15 主题不设上限，默认「均衡模式」（你 2026-10-23 拍板：均衡 = 我没有特定倾向，想直接靠 AI 推荐）**
- 现状：最多选 3 个，一句话填表也只读前 3 个；混选的权重基本不起作用（Q1 基线）。
- 「均衡」是什么：**我不知道这座城市哪里好玩、没有特定倾向，请直接推荐**。做法：先保证这座城市的**标志性地点**（城市配置里的 landmarks）排进去，再按各主题**等权**补充，让每个主题都有点；说明文字（模型写）里写清「为什么推荐这些」——选哪些点永远由确定性的排程器按核对过的地点库决定，模型只负责把理由讲清楚，不会编地点。
- 目标：主题区第一项是「均衡 · 让我来推荐」，**默认选中**；点具体主题 = 说明你有倾向，「均衡」取消，想选几个选几个（不设上限），每个所选主题的权重仍可调（1–5）；把具体主题都取消 = 回到均衡。行程页标题 / 封面写「均衡」或「艺术 + 美食 + …」。一句话填表同样不再只读前 3 个主题。
- 前端：打开新建页，默认就是「均衡」选中；点「艺术」「美食」「摄影」「购物」「时尚」「博物馆」六个，不报错、可以生成，行程里这六个主题都有点；全部取消回到「均衡」。
- 排程这一半（权重真正起作用、每个主题至少 2 个点、每天至少 2 个点）归 Q3 的第二半（见「二点六」），验收用 Q1 基线。

### 行程页（Q4）

- 前端：一天的时间轴一屏能看到至少 4 个条目；点名字旁的「详情 ›」弹出浮窗，信息一样不少。

## 二点五、Q1 排程评测基线（你 2026-10-23 拍板开始）

目的：给 Q3（主题不设上限、时长建议）和 Q5（长行程）一把尺子——改之前量一次，改之后再量，指标不退步才算过。**只量确定性的排程器**（不调模型），所以每次结果完全一样。

- **请求集**：20 份固定请求（`tests/fixtures/schedule/requests.json`）：8 个主题各 4 天；节奏（轻松 / 紧凑）、2 天和 5 天；周一 / 周二开头（闭馆日敏感）；必去 + 不去；2 个混选（均衡 / 5-3-1 权重）；3 个主题 7 天；单主题 7 天、10 天（长行程）。另有「探针」：4 个以上主题（现在会被拒绝；绕过校验直接问排程器，看它撑不撑得住）。
- **指标**（每份请求）：硬约束违例（质检 error，目标 0）、警告数；每天主要点数（最少 / 平均）；顺手补的小点数；空档分钟（总计 / 最长）；午餐 / 晚餐覆盖的天数；直线公里（总计 / 最远一天 / 超过 3 公里的单段数）；通勤总分钟；重复地点数；每个所选主题的点数占比和与权重的偏差（混选用）；排程耗时。
- **产出**：`scripts/eval_schedule.py` 打印表格并写 `docs/reports/q1-schedule-baseline.md`（含「解读」）；`tests/fixtures/schedule/baseline.json` 是确定性部分的快照，`tests/test_eval_schedule.py` 对比它——排程器的任何改动让指标变了，测试会指出是哪份请求的哪个指标；确认新结果是想要的之后用 `--write-baseline` 重录。

- **超长行程的提示**：`suggested_days` 多一个可选的 `fill_max`（这座城市的点最多能把几天排满，每天 ≥ 2 个）；巴黎 `quality_max` 14、`fill_max` 22（实测：8 个主题 22 天都排得满，23 天起文娱开始缺）。新建页的时长提示按三档：≤ 14 天「偏长，后面几天的点会没那么精彩，节奏默认放宽到轻松」；15–22 天「主题里的点不够，后面大多会排其他主题的代表性景点」；> 22 天「巴黎的点最多排满约 22 天，多出来的天会留成自由日」。**只提醒，不拦，可以照样生成**。
- **排不满的天**：库里实在没有这天开放、排得进的点，这天写成「自由安排」（修了上面的报错）；以前每个这样的天一条说明，现在合成一条（「N 天排不满（日期……）：……这几天排得比较少，空出来的时间留作自由安排」）。
- **封面卡片的名字不再被吞（你 10-29 的截图：「皮诺艺术收藏馆…」）**：行程页封面的亮点卡片，景点名最多两行，不再单行加省略号。
- **不做**：更长的旅行靠多城市（K3，已做完，见 [11](11-multi-city.md)），不把巴黎硬拉长。

## 四、验收方式

- **自动化**：每条的验收场景写成 Playwright 用例（沿用独立栈）；排程相关（P06 / P15）用 Q1 的基线对比（硬约束违例 0、各主题都有点、排程耗时不显著变长）。
- **前端**：每个批次结束，我按上面「前端」那一行给你点击步骤。
- **不做**：登录 / 证件号 / 在线订票。
